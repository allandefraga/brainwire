# v0.13 memory diagnostics — 2026-10-30

These are short synthetic diagnostics, **not a production memory qualification**
or a comparison with other databases. They ran against a locally built Linux
arm64 image from source `88fc9544ef26b244d4f7950d9d17deaeba58b9cf`, on a
shared Docker Desktop VM. The local image ID was
`sha256:38f3b41e3c7f5fb6169b4fef5ab3d5f72df5c82f92f4f23bb8408db8505565e9`;
it is not the published release image digest. Other workloads were present.
Raw receipts are retained locally because they contain host telemetry.

## 512 MiB pressure and recovery

Three isolated runs of `crates/server/tests/cgroup_pressure_smoke.py` passed.
Each induced temporary cgroup pressure, observed `MemoryPressure` on new work,
checked rollback and confirmed data, relieved pressure, and audited the graph.
The sampled cgroup `oom` and `oom_kill` counters did not increase. Each run
removed its own temporary resources. This does not independently inspect the
host kernel log or establish an RSS ceiling, sustained-load stability, power
loss recovery, or distributed failover.

## 100,000-row short load

A separate single run used the same image with 100,000 synthetic nodes, a
4,096-byte payload per node, two CPUs and a 4 GiB container limit, followed by
60 seconds idle. It completed in 5.58 seconds; process peak RSS was 223.1 MiB,
final idle RSS was 194.8 MiB and peak cgroup usage was 238.2 MiB. The graph
count and offline audit passed; sampled cgroup OOM counters did not increase.
The fixture repeats the same easily compressed payload, the host was shared,
and this was one short run. These figures do not predict real ingestion
throughput or the 1-million-node, sustained 2/4/8 GiB workload.

## Idle allocator diagnostic

Six runs used `allocator_decay_probe.py` on the same local image: 10,000
synthetic rows, 4,096-byte payloads, batches of 250, 30 seconds idle, two CPUs
and a 4 GiB container limit. Three runs used 10,000 ms jemalloc decay and three
used 1,000 ms. Each startup configuration was confirmed in jemalloc diagnostics; this does
not prove later per-arena settings or that every C++ allocation uses jemalloc.
The values below are process RSS, not total cgroup usage:

| Decay | Peak RSS (MiB), three runs | Final idle RSS (MiB), three runs |
| --- | --- | --- |
| 10,000 ms | 179.8, 176.7, 126.8 | 134.6, 132.1, 103.0 |
| 1,000 ms | 175.1, 165.1, 163.9 | 131.0, 123.0, 121.0 |

The run order was not randomized, the machine was shared, and the large
variation prevents choosing a better production default from these samples.
The first attempt was inconclusive because the diagnostic did not recognize
jemalloc's actual log prefix. The parser was corrected on `main`, then all six
runs above passed. No allocator default was changed.

Reproduce with a locally built image and the Python Bolt driver. The corrected
probe is on `main`; the `v0.13.0-beta.1` tag predates that diagnostic fix.
Run each setting multiple times on an isolated host, saving a new output file:

```sh
python crates/server/tests/allocator_decay_probe.py \
  --image <local-image> --output <new-receipt.json> --decay-ms 10000 \
  --rows 10000 --batch 250 --payload-bytes 4096 --idle-seconds 30
```

Repeat with `--decay-ms 1000`. Compare the same image, environment, fixture and
configuration; never interpret this short test as the missing 2/4/8 GiB soak.
